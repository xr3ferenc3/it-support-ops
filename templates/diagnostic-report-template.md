# Diagnostic Report Template

## Purpose

This template provides a structured format for documenting diagnostic findings
as a standalone attachment to a support ticket. It is used when the volume of
diagnostic data - script output, test results, observations - is too large to
include cleanly in the ticket notes field, or when the findings need to be shared
with a Tier 2 technician or vendor as a concise diagnostic package.

A diagnostic report attached to a ticket demonstrates that troubleshooting was
methodical, evidence-based, and complete. It is the primary evidence in an
escalation and the primary reference for a technician who picks up the ticket later.

---

## When to Use This Template

Use this template when:

- Running one or more diagnostic scripts and attaching output to a ticket
- Preparing an escalation package for Tier 2 or Tier 3
- Documenting findings for a complex fault where the ticket notes field is insufficient
- Producing a diagnostic record that a vendor may need to review

For standard tickets where findings fit cleanly in the ticket notes, the
diagnostic steps fields in [`ticket-template.md`](ticket-template.md) are sufficient.
This template is for cases where a separate document is warranted.

## DIAGNOSTIC REPORT TEMPLATE

```
================================================================================
IT SUPPORT - DIAGNOSTIC REPORT
================================================================================

REPORT REFERENCE:       [Ticket Number]-DIAG-[Date: YYYYMMDD]
DATE GENERATED:         [YYYY-MM-DD HH:MM]
GENERATED BY:           [Technician name and role]
TICKET REFERENCE:       [Associated ticket number]

────────────────────────────────────────────────────────────────────────────────
SECTION 1 - SUBJECT SYSTEM
────────────────────────────────────────────────────────────────────────────────

Hostname:               [Computer name]
Operating System:       [OS name and version]
Asset Tag:              [If applicable]
Primary User:           [Name and department]
Connection Type:        [Wired / Wi-Fi / VPN / N/A]
Location:               [Physical location or "Remote"]
Report Generation Time: [YYYY-MM-DD HH:MM]

────────────────────────────────────────────────────────────────────────────────
SECTION 2 - PRESENTING PROBLEM
────────────────────────────────────────────────────────────────────────────────

Reported Symptom:
  [What the user reported, in their words where possible]

Observable Symptoms (Technician):
  [What the technician independently observed - error messages, system state,
  behaviour - separate from what the user described]

Time of Fault Onset:
  [When the fault started - from user report and confirmed if possible]

Related Changes:
  [Anything that changed before the fault started]

────────────────────────────────────────────────────────────────────────────────
SECTION 3 - SYSTEM HEALTH SNAPSHOT
────────────────────────────────────────────────────────────────────────────────

[Complete this section by running the appropriate diagnostic script and either
pasting key findings here or referencing the attached script output file.]

Script(s) Run:
  [ ] Get-SystemHealthReport.ps1      Output file: ___________________
  [ ] Get-NetworkDiagnostics.ps1      Output file: ___________________
  [ ] Get-DiskHealthReport.ps1        Output file: ___________________
  [ ] Get-EventLogSummary.ps1         Output file: ___________________
  [ ] Test-ConnectivitySuite.ps1      Output file: ___________________
  [ ] system-health-report.sh         Output file: ___________________
  [ ] network-diagnostics.sh          Output file: ___________________
  [ ] disk-health-report.sh           Output file: ___________________
  [ ] log-summary.sh                  Output file: ___________________
  [ ] connectivity-suite.sh           Output file: ___________________

Key Findings from Script Output:

  CPU Status:
    [Current usage, peak observed, any flagged processes - or "See attached"]

  Memory Status:
    [Usage percentage, available, any flagged processes - or "See attached"]

  Disk Status:
    [Free space per volume, any health flags - or "See attached"]

  Network Status:
    [IP address, gateway, DNS, any APIPA/fault flags - or "See attached"]

  Event Log / Journal Highlights:
    [Significant errors or warnings found, Event IDs if applicable - or "See attached"]

────────────────────────────────────────────────────────────────────────────────
SECTION 4 - DIAGNOSTIC TEST SEQUENCE
────────────────────────────────────────────────────────────────────────────────

[Document each diagnostic test in order. This section is the primary evidence
of structured troubleshooting methodology. Do not omit steps or results.]

TEST 1
  Time:       [HH:MM]
  Test:       [What was tested - e.g. "Ping to default gateway 192.168.1.1"]
  Command:    [Exact command run if applicable]
  Result:     [Exact result - e.g. "4/4 replies received, avg 1ms"]
  Conclusion: [What this result means for the diagnosis]

TEST 2
  Time:       [HH:MM]
  Test:       [What was tested]
  Command:    [Exact command]
  Result:     [Exact result]
  Conclusion: [Conclusion]

TEST 3
  Time:       [HH:MM]
  Test:       [What was tested]
  Command:    [Exact command]
  Result:     [Exact result]
  Conclusion: [Conclusion]

TEST 4
  Time:       [HH:MM]
  Test:       [What was tested]
  Command:    [Exact command]
  Result:     [Exact result]
  Conclusion: [Conclusion]

TEST 5
  Time:       [HH:MM]
  Test:       [What was tested]
  Command:    [Exact command]
  Result:     [Exact result]
  Conclusion: [Conclusion]

(Continue for all tests performed)

────────────────────────────────────────────────────────────────────────────────
SECTION 5 - FAULT ISOLATION SUMMARY
────────────────────────────────────────────────────────────────────────────────

[For network faults, complete the layer-by-layer summary below.
For non-network faults, use the generalised isolation summary instead.]

NETWORK FAULT ISOLATION (complete if a network fault):

  Layer 1 (Physical):      [PASS / FAIL / NOT TESTED - findings]
  Layer 2 (Data Link):     [PASS / FAIL / NOT TESTED - findings]
  Layer 3 (Network/IP):    [PASS / FAIL / NOT TESTED - findings]
  Layer 4 (Transport):     [PASS / FAIL / NOT TESTED - findings]
  Layer 7 (Application):   [PASS / FAIL / NOT TESTED - findings]

  Fault Boundary:          [Layer where the first failure was identified, or
                            "Not identified at Tier 1"]

GENERAL FAULT ISOLATION (complete if not a network fault):

  Hardware checked:        [Yes - findings / No / N/A]
  OS-level checked:        [Yes - findings / No / N/A]
  Application checked:     [Yes - findings / No / N/A]
  Permissions checked:     [Yes - findings / No / N/A]
  Configuration checked:   [Yes - findings / No / N/A]

────────────────────────────────────────────────────────────────────────────────
SECTION 6 - HYPOTHESIS AND ROOT CAUSE ASSESSMENT
────────────────────────────────────────────────────────────────────────────────

Initial Hypothesis:
  [What the probable cause was assessed to be at intake, and why]

Hypothesis Tested:
  [Yes - confirmed / Yes - refuted / Partially - explain]

Revised Hypothesis (if initial was refuted):
  [Updated suspected cause after testing]

Root Cause Assessment:

  Status: [CONFIRMED / SUSPECTED / UNCONFIRMED]

  [If CONFIRMED:]
  Root Cause:
    [Specific technical explanation of why the fault occurred]

  [If SUSPECTED or UNCONFIRMED:]
  Most Probable Cause:
    [Best current assessment with the evidence available]

  Evidence Supporting This Assessment:
    [List the specific test results that support the hypothesis]

  Evidence That Could Not Be Confirmed:
    [What would confirm or refute this hypothesis - and why it could not be
    tested at Tier 1 - this becomes the escalation request]

────────────────────────────────────────────────────────────────────────────────
SECTION 7 - ACTIONS TAKEN
────────────────────────────────────────────────────────────────────────────────

[List every action taken on the system, in order. Include actions that were
reversed. This provides a complete audit trail for the receiving technician
and prevents duplicate steps during escalation.]

  [YYYY-MM-DD HH:MM] Action: [Description of what was done]
    Outcome: [Result of the action]

  [YYYY-MM-DD HH:MM] Action: [Description]
    Outcome: [Result]

  [YYYY-MM-DD HH:MM] Action: [Description]
    Outcome: [Result]

Current System State:
  [Description of the system's current state at the time of this report -
  what is still failing, what has been partially resolved, whether a workaround
  is in place]

────────────────────────────────────────────────────────────────────────────────
SECTION 8 - ESCALATION REQUEST (COMPLETE IF ESCALATING)
────────────────────────────────────────────────────────────────────────────────

Escalating to:          [Tier 2 technician or team name]
Escalation Priority:    [P1 / P2 / P3]
Specific Request:
  [Exactly what Tier 2 is being asked to do - be specific.
  "Please investigate" is not acceptable.
  "Please access the DHCP server and confirm whether the scope for the
  192.168.1.x range is exhausted" is acceptable.]

Business Impact at Escalation Time:
  [Number of users affected, any business deadline, operational risk]

Workaround in Place:
  [Yes - describe / No]

Attachments:
  [ ] Diagnostic script output files (list filenames):
      _______________________________________________
  [ ] Screenshots of error messages
  [ ] Event log exports
  [ ] Other: _______________________________________

================================================================================
END OF DIAGNOSTIC REPORT
================================================================================
```

## Report Naming Convention

Use a consistent naming convention when saving diagnostic reports for ticket attachment:

```
[TicketNumber]-DIAG-[YYYYMMDD]-[Hostname].txt

Examples:
  INC0012345-DIAG-20250615-WKSTN-042.txt
  INC0012345-DIAG-20250615-WKSTN-042-NetworkDiagnostics.txt
```

When attaching multiple reports (e.g. system health and network diagnostics),
name each file to indicate which script generated it.

## Section Completion Guidance

| Section | When to Complete | Minimum Content |
|---|---|---|
| 1 - Subject System | Always | All fields |
| 2 - Presenting Problem | Always | Reported symptom + technician observations |
| 3 - System Health Snapshot | Always when scripts were run | Tick scripts used; paste key findings or reference attached files |
| 4 - Diagnostic Test Sequence | Always | Every test with command, result, and conclusion |
| 5 - Fault Isolation Summary | Always | Network layer table if network fault; general if not |
| 6 - Hypothesis Assessment | Always | Initial hypothesis + confirmed/suspected/unconfirmed root cause |
| 7 - Actions Taken | Always | Every action with timestamp and outcome; current state |
| 8 - Escalation Request | Only when escalating | Specific request, business impact, attachments listed |

---

## Security Considerations

- Diagnostic reports may contain IP addresses, hostnames, usernames, and system
  configuration details - treat as internal-confidential and share only with
  personnel who need the information to resolve the fault
- Script output attached to diagnostic reports should be reviewed before sharing
  externally (with vendors) - remove or redact sensitive internal addressing,
  domain names, or user account information as appropriate
- Reports generated during a security incident investigation should be stored
  separately from standard ticket attachments and access-controlled accordingly
