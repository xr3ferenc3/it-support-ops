# Sample: Completed Linux Diagnostic Report

## About This Sample

This is a completed example of the
[`../templates/diagnostic-report-template.md`](../templates/diagnostic-report-template.md)
for a Linux endpoint scenario: a user on an Ubuntu 22.04 workstation reported that
an application they use daily was crashing immediately on launch. The diagnostic
process identified a corrupted user configuration directory caused by an unclean
shutdown the previous day.

This sample demonstrates:

- How Linux-specific diagnostic tools (`journalctl`, `coredumpctl`, `df -i`) are
  applied within the same structured methodology used for Windows
- How the general fault isolation table (non-network) is completed
- How a confirmed root cause is documented with supporting evidence
- What a complete Tier 1 resolution record looks like when escalation is not required

All hostnames, usernames, and IP addresses are fictional. Adapt for your environment.

---

Related Changes:
  User reports no intentional changes. Power went out briefly in Building B
  yesterday evening at approximately 18:20 - the user had already left but the

────────────────────────────────────────────────────────────────────────────────

Script(s) Run:
  [x] system-health-report.sh         Output file: INC0008512-SystemHealth.txt

────────────────────────────────────────────────────────────────────────────────
SECTION 4 - DIAGNOSTIC TEST SEQUENCE
────────────────────────────────────────────────────────────────────────────────

TEST 1
  Time:       09:58
  Test:       Confirm disk space and inodes are not the cause
  Command:    df -h && df -i
  Result:     / : 67% capacity used, 41% inodes used
              /home : 81% capacity used, 38% inodes used
              No filesystem at critical levels.
  Conclusion: Disk space and inode exhaustion ruled out as cause.

TEST 2
  Time:       10:02
  Test:       Check system journal for application crash detail
  Command:    journalctl --since "yesterday" -p warning | grep -i projectapp
  Result:     2025-06-15 18:21:09 kernel: system halted
              2025-06-16 09:16:42 kernel: projectapp-desktop[8841]: segfault
              at 0 ip 00007f3a2b4c1d20 sp 00007fff3e2a1b90 error 4
              in libprojectapp-core.so.3[7f3a2b400000+100000]
              2025-06-16 09:17:03 kernel: projectapp-desktop[8864]: segfault
              (same fault address and shared library - reproducible crash)
  Conclusion: Application is crashing with a segmentation fault in a shared
              library (libprojectapp-core.so.3) immediately after launch.
              Unclean shutdown confirmed at 18:21:09 yesterday - power loss
              event correlates with fault onset.

TEST 3
  Time:       10:05
  Test:       Check for core dump for additional detail on crash location
  Command:    coredumpctl list | grep projectapp
  Result:     Mon 2025-06-16 09:16:42 projectapp-desktop (sig:11 SIGSEGV)
              Mon 2025-06-16 09:17:03 projectapp-desktop (sig:11 SIGSEGV)
  Conclusion: Two core dumps captured, both SIGSEGV (segmentation violation)
              in the same shared library. Pattern consistent with corrupted
              application data rather than a code defect (same library, same
              offset, reproducible on second launch).

TEST 4
  Time:       10:08
  Test:       Check for broken package installation or missing library
  Command:    dpkg --verify projectapp-desktop 2>&1
              ldd /usr/bin/projectapp-desktop | grep "not found"
  Result:     dpkg --verify: no output (package files intact, checksums valid)
              ldd: no "not found" entries - all shared libraries present and
              accessible.
  Conclusion: Package installation and shared library dependencies are intact.
              The fault is not a missing library or corrupted binary.
              Corrupted user-specific configuration is now the primary suspect.

TEST 5
  Time:       10:12
  Test:       Check whether the application launches for a different user
              (confirms whether fault is user-specific or system-wide)
  Command:    su -c "projectapp-desktop &" testuser
              [testuser is the IT support local test account]
  Result:     Application launched successfully for testuser. GUI appeared
              and remained stable. No crash observed.
  Conclusion: Fault is user-specific - confirmed NOT a system-wide application
              or shared library fault. The corruption is in F. Osei's user
              profile or application configuration directory.

TEST 6
  Time:       10:15
  Test:       Locate and inspect the user's application configuration directory
  Command:    ls -la /home/fosei/.config/projectapp/
              ls -la /home/fosei/.local/share/projectapp/
  Result:     /home/fosei/.config/projectapp/ - present, last modified
              2025-06-15 18:21 (matches the unclean shutdown timestamp exactly)
              /home/fosei/.local/share/projectapp/ - present, no anomalies

              Within ~/.config/projectapp/:
              -rw-r--r-- fosei fosei  0 Jun 15 18:21 preferences.json
              -rw-r--r-- fosei fosei  0 Jun 15 18:21 workspace.json
              -rw-r--r-- fosei fosei  0 Jun 15 18:21 recent-projects.json

              All three configuration files are 0 bytes. These should contain
              JSON data but were truncated during the power loss while being
              written by the application on shutdown.
  Conclusion: Root cause confirmed. Configuration files were corrupted (zeroed)
              during the unclean shutdown. Application attempts to parse these
              empty files on launch, encounters invalid JSON, and crashes with
              SIGSEGV in the configuration parsing library.

────────────────────────────────────────────────────────────────────────────────
SECTION 5 - FAULT ISOLATION SUMMARY
────────────────────────────────────────────────────────────────────────────────

GENERAL FAULT ISOLATION:

  Hardware checked:        Yes - SMART health PASSED, disk capacity adequate,
                           no hardware flags from system-health-report.sh
  OS-level checked:        Yes - OS itself functioning normally; other
                           applications unaffected; system journal reviewed
  Application checked:     Yes - package integrity verified (dpkg --verify);
                           shared libraries present; binary intact
  Permissions checked:     Yes - configuration files owned by correct user
                           (fosei:fosei), permissions 644 - no access issues
  Configuration checked:   Yes - ROOT CAUSE FOUND: three configuration files
                           in ~/.config/projectapp/ are 0 bytes following
                           unclean shutdown on 2025-06-15 18:21

────────────────────────────────────────────────────────────────────────────────
SECTION 6 - HYPOTHESIS AND ROOT CAUSE ASSESSMENT
────────────────────────────────────────────────────────────────────────────────

Initial Hypothesis:
  Application binary or shared library corruption following unclean shutdown.
  The power loss event at 18:21 was the strongest candidate for a fault
  that appeared functional before and broken after a single event.

Hypothesis Tested:
  Yes - PARTIALLY REFUTED. Binary and library integrity confirmed intact
  (dpkg --verify, ldd - no missing libraries). Root cause was configuration
  file corruption, not binary corruption. The general hypothesis (shutdown
  corruption) was correct; the specific location was refined through testing.

Root Cause Assessment:

  Status: CONFIRMED

  Root Cause:
    Three JSON configuration files in /home/fosei/.config/projectapp/
    (preferences.json, workspace.json, recent-projects.json) were truncated to
    0 bytes during the unclean system shutdown caused by a power loss event at
    18:21 on 2025-06-15. The application was in the process of writing these
    files during shutdown and the write was incomplete when power was lost.
    On next launch, the application attempts to parse these files, encounters
    empty/invalid JSON, and crashes with SIGSEGV in the configuration parsing
    routine (libprojectapp-core.so.3).

  Evidence Supporting This Assessment:
    1. Unclean shutdown confirmed in journal at 2025-06-15 18:21:09
    2. Configuration files have modification timestamp of exactly 18:21
       (matching the shutdown event)
    3. All three configuration files are 0 bytes (expected: valid JSON)
    4. Application launches successfully for testuser (not affected by
       fosei's configuration directory)
    5. SIGSEGV in libprojectapp-core.so.3 at consistent fault address
       (parser encountering unexpected data - empty buffer)
    6. Binary and shared library integrity confirmed intact

────────────────────────────────────────────────────────────────────────────────
SECTION 7 - ACTIONS TAKEN
────────────────────────────────────────────────────────────────────────────────

  [2025-06-16 10:18] Action: Backed up corrupted configuration directory
  before modification
    Command: cp -r /home/fosei/.config/projectapp/
    /home/fosei/.config/projectapp_backup_20250616_1018/
    Outcome: Backup created successfully. Confirmed backup contains the same
    0-byte files (preserving original state for reference).

  [2025-06-16 10:19] Action: Removed corrupted configuration directory to
  allow application to regenerate defaults on next launch
    Command: rm -rf /home/fosei/.config/projectapp/
    Outcome: Directory removed. Application can now create fresh configuration
    on next launch.

  [2025-06-16 10:20] Action: Launched application as F. Osei to confirm
  configuration regeneration and successful startup
    Command: [Launched from application menu while logged in as F. Osei]

## What This Sample Demonstrates

**Using `journalctl` as primary diagnostic evidence (Test 2):** The journal
entry not only confirmed the application crash but included the exact shared
library and fault address, and the unclean shutdown timestamp - giving the
technician a clear time correlation that would have taken much longer to
establish without structured log review.

**The user-isolation test (Test 5):** Launching the application as a different
user before touching any configuration is a critical step that many technicians
skip. It confirmed in under one minute that the fault was user-specific rather
than system-wide - this finding alone prevented unnecessary reinstallation of
the application and its dependencies.

**Backing up before modifying (Section 7, Action 1):** Even when the root
cause is clear and the fix is simple, a backup of the corrupted state is taken
before removal. This documents the state of the system, provides the backup if
the initial diagnosis is wrong, and protects the technician if the user later
claims data was lost during the repair.

**Precise root cause statement (Section 6):** The root cause does not say
"the application config was broken." It identifies the specific files, explains
the mechanism (write interrupted during power loss), describes the crash pathway
(empty buffer parsed as JSON), and references the corroborating evidence. This
is the level of specificity that enables prevention recommendations.
