# Sample: Completed Windows Diagnostic Report

## About This Sample

This is a completed example of the
[`../templates/diagnostic-report-template.md`](../templates/diagnostic-report-template.md)
for a real-world scenario: a user reported "no internet access" and the diagnostic
process identified an APIPA address caused by a DHCP scope exhaustion event.

This sample demonstrates:

- How diagnostic script output is summarised into the report rather than pasted raw
- How the Layer 1–7 fault isolation sequence is documented
- How the escalation request section is completed with a specific, actionable ask
- How timestamps are applied throughout
- What a complete, professional diagnostic record looks like at escalation time

All hostnames, IP addresses, and usernames are fictional (RFC 5737 documentation
range IPs: 192.0.2.x). Adapt this sample for your own environment.

---

  User reports no changes to their workstation. No Windows Update reboots

────────────────────────────────────────────────────────────────────────────────

────────────────────────────────────────────────────────────────────────────────

Script(s) Run:
  [x] Get-SystemHealthReport.ps1      Output file: INC0008471-SystemHealth.txt

  [ ] Test-ConnectivitySuite.ps1      (Replaced by manual staged testing below)

Key Findings from Script Output:

  CPU Status:
    Average usage 8% at time of collection. No runaway processes identified.
    System is otherwise healthy - fault is isolated to networking.

  Memory Status:
    5.2GB used of 16GB (33%). No memory pressure contributing to fault.

  Disk Status:
    C: drive 74% used (68.4GB free of 238GB). No disk health flags.

  Network Status:
    FAULT DETECTED - Get-NetworkDiagnostics.ps1 output:

    Layer 3:   IPv4 Address: 169.254.43.201 (APIPA)

               DHCP Server: [none - DHCP failed]
    FAULT BOUNDARY IDENTIFIED: Layer 3 (Network) - APIPA / DHCP failure
    (Full report in attached INC0008471-NetworkDiag.txt)

  Event Log Highlights:
    Event ID 1003 (DHCP client): "Your computer was not able to renew its
    address from the network (from the DHCP Server) for the Network Card with
    network address [MAC]. The following error occurred: The operation was
    cancelled by the user. Your computer will continue to try to obtain an
    address on its own from the network address (DHCP) server."
    First occurrence: 2025-06-15 07:43:18 (system startup)
    Subsequent occurrences: 07:43:19, 07:58:19, 08:13:19 (every 15 minutes -
    standard DHCP retry interval)

────────────────────────────────────────────────────────────────────────────────
SECTION 4 - DIAGNOSTIC TEST SEQUENCE
────────────────────────────────────────────────────────────────────────────────

TEST 1
  Time:       09:12
  Test:       Confirm adapter physical status and link light
  Command:    Get-NetAdapter | Select Name, Status, LinkSpeed, MacAddress
  Result:     Name: Ethernet | Status: Up | LinkSpeed: 1 Gbps | MAC: present
  Conclusion: Layer 1 confirmed. Physical connection and NIC are functional.

TEST 2
  Time:       09:13
  Test:       View full IP configuration to confirm APIPA and absence of gateway
  Command:    ipconfig /all
  Result:     IPv4: 169.254.43.201 | Subnet: 255.255.0.0 | Gateway: [blank]
              DHCP Enabled: Yes | DHCP Server: [blank]
              Lease Obtained: N/A | Lease Expires: N/A
  Conclusion: APIPA confirmed. DHCP server not reached since last reboot.
              Layer 3 fault confirmed.

TEST 3
  Time:       09:15
  Test:       Attempt DHCP release and renew
  Command:    ipconfig /release && ipconfig /renew
  Result:     Release succeeded (address removed). Renew returned:
              "An error occurred while renewing interface Ethernet : unable to
              contact your DHCP server. Request has timed out."
              APIPA address reassigned: 169.254.43.201
  Conclusion: DHCP server is not responding to discovery broadcasts on this
              network segment. This is not an isolated client fault.

TEST 4
  Time:       09:18
  Test:       Check whether other devices on the same floor are affected
  Command:    [Physical check - walked to nearby desks F2-12 and F2-16]
  Result:     Both F2-12 and F2-16 also show APIPA addresses. F2-12 user
              (K. Adeyemi) had not yet reported the fault. F2-16 is unoccupied.
              Checked with reception on Floor 1 - no issues reported there.
  Conclusion: Fault is at minimum departmental scope on Floor 2. Possible
              floor-switch-level DHCP relay fault, or DHCP scope exhaustion for
              the Floor 2 subnet.

TEST 5
  Time:       09:21
  Test:       Attempt static IP workaround to confirm routing is otherwise intact
  Command:    New-NetIPAddress -InterfaceIndex 4 -IPAddress "192.0.2.200"
              -PrefixLength 24 -DefaultGateway "192.0.2.1"
              Set-DnsClientServerAddress -InterfaceIndex 4
              -ServerAddresses ("192.0.2.10")
              ping 192.0.2.1
  Result:     ping 192.0.2.1 - 4/4 replies received, avg 1ms.
              ping 8.8.8.8 - 4/4 replies received, avg 14ms.
              nslookup google.com - resolved successfully.
  Conclusion: Layer 1–7 functional once a valid static IP is provided. The
              fault is exclusively that DHCP is not issuing leases to this
              subnet. Gateway and upstream routing are intact.
              Static IP documented as temporary workaround - removed after test.

TEST 6
  Time:       09:26
  Test:       Confirm DHCP server identity and check if it is reachable
  Command:    [Checked with IT documentation for DHCP server address - SRV-DHCP01
              at 192.0.2.5]
              ping 192.0.2.5 -n 4
  Result:     4/4 replies received, avg 1ms. DHCP server is online and
              network-reachable.
  Conclusion: The DHCP server is reachable. The fault is not a downed server.
              Most likely cause: DHCP scope for Floor 2 subnet (192.0.2.0/24)
              is exhausted - all addresses issued, no leases available for
              renewal or new requests. Requires Tier 2 access to the DHCP
              server console to verify and extend or clear stale leases.

────────────────────────────────────────────────────────────────────────────────
SECTION 5 - FAULT ISOLATION SUMMARY
────────────────────────────────────────────────────────────────────────────────

NETWORK FAULT ISOLATION:

  Layer 1 (Physical):      PASS - Link UP at 1Gbps, NIC detected, MAC valid
  Layer 2 (Data Link):     PASS - No ARP issues detected, MAC-level communication
                                  functional (gateway reachable with static IP)
  Layer 3 (Network/IP):    FAIL - APIPA address assigned; DHCP renewal times out;
                                  no default gateway when using DHCP
  Layer 4 (Transport):     NOT TESTED (Layer 3 failure makes this unnecessary)
  Layer 7 (Application):   NOT TESTED (Layer 3 failure makes this unnecessary)

  Fault Boundary:          Layer 3 - DHCP failure. DHCP server is reachable and
                           responding to ICMP but not issuing leases to the Floor 2
                           subnet (192.0.2.0/24). Suspected scope exhaustion.

────────────────────────────────────────────────────────────────────────────────
SECTION 6 - HYPOTHESIS AND ROOT CAUSE ASSESSMENT
────────────────────────────────────────────────────────────────────────────────

Initial Hypothesis:
  DHCP lease expiry on individual workstation following overnight offline period.
  This is the most common cause of APIPA on a device that was previously working.

Hypothesis Tested:
  Yes - REFUTED. ipconfig /renew failed with a timeout, indicating the DHCP
  server itself is not responding to requests on this subnet. If the fault were
  a simple lease expiry, /renew would have succeeded.

Revised Hypothesis:
  DHCP scope exhaustion for the Floor 2 subnet. The DHCP server is online and
  reachable, but appears to have no available addresses to allocate. Evidence:
  multiple devices on Floor 2 simultaneously have APIPA addresses; DHCP server
  is reachable by ICMP; renew request times out without a response from the server.

Root Cause Assessment:

  Status: SUSPECTED (confirmation requires server-side access)

  Most Probable Cause:
    The DHCP scope for the Floor 2 subnet (192.0.2.0/24) has become exhausted -
    all configured IP addresses in the lease pool have been allocated and none
    have expired, preventing new or renewing leases from being issued.

  Evidence Supporting This Assessment:
    1. Multiple Floor 2 devices simultaneously show APIPA addresses
    2. DHCP server is reachable by ping (server is up)
    3. DHCP renew request times out without acknowledgement (no available address
       to offer) rather than being explicitly rejected
    4. Layer 1–2 confirmed functional; fault is exclusively DHCP-level
    5. Floor 1 devices are unaffected (separate subnet/scope)

  Evidence That Could Not Be Confirmed:
    Cannot confirm scope exhaustion without access to the DHCP server console
    (SRV-DHCP01). Requires Tier 2 to review active leases, scope utilisation,
    and whether stale/orphaned leases can be cleared.

────────────────────────────────────────────────────────────────────────────────
SECTION 7 - ACTIONS TAKEN
────────────────────────────────────────────────────────────────────────────────

  [2025-06-15 09:15] Action: Attempted DHCP release and renew (ipconfig /release
  && ipconfig /renew)
    Outcome: Renew timed out. APIPA reassigned. No change in connectivity.

  [2025-06-15 09:21] Action: Applied temporary static IP (192.0.2.200/24,
  gateway 192.0.2.1, DNS 192.0.2.10) to confirm routing path was intact
    Outcome: Static IP restored full Layer 3–7 connectivity. User confirmed
    internet and internal resources accessible with static IP applied.

  [2025-06-15 09:24] Action: Removed static IP workaround after routing
  confirmation - reverted to DHCP pending Tier 2 resolution
    Outcome: APIPA address returned as expected. Workaround removed to avoid
    a permanent static IP assignment in the DHCP range without coordination.

  [2025-06-15 09:28] Action: Applied documented static IP workaround per
  IT addressing policy (using reserved range 192.0.2.190–199 per network docs)
  to restore user productivity while escalation is handled
    Outcome: User J. Nkemdirim confirmed ability to access email, file server,
    and internet. Workaround active. Documented in ticket.

Current System State:
  Workstation WKSTN-042 is operational using a temporary static IP (192.0.2.195).
  DHCP lease is not active. Static IP must be reverted to DHCP once Tier 2
  resolves the scope exhaustion. Two additional Floor 2 workstations (F2-12,
  F2-16) remain on APIPA - their users have been notified. Scope currently
  estimated to be affecting all Floor 2 DHCP clients.

────────────────────────────────────────────────────────────────────────────────

Escalating to:          B. Mwangi - Senior Systems Administrator (Tier 2)

                        Floor 2 users)

  Please access SRV-DHCP01 and:

Workaround in Place:

## What This Sample Demonstrates

This completed report shows several professional practices that distinguish
a structured technician from one who relies on intuition:

**Scope confirmation at Step 4:** Rather than treating the APIPA address as an
isolated device fault, the technician physically checked adjacent workstations
before escalating. This confirmed a departmental scope, changed the priority,
and gave Tier 2 the correct picture of the incident immediately.

**Hypothesis revision at Step 3:** The initial hypothesis (simple lease expiry)
was tested and explicitly refuted by the renew timeout result. The report documents
this revision rather than silently replacing the initial hypothesis - this is the
scientific thinking that structured troubleshooting requires.

**Static IP test as diagnostic tool (Step 5):** Using a temporary static IP to
confirm that routing, DNS, and internet egress were intact was not a resolution
attempt - it was a targeted test to rule out a Layer 3+ routing fault and confirm
that the fault was exclusively DHCP. The test was reversed after confirmation.

**Specific escalation request (Section 8):** The request to Tier 2 is three
numbered, specific actions with the exact subnet range and DHCP scope bounds
referenced from IT documentation - not "please look at the DHCP server."
